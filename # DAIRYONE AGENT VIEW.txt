# DAIRYONE AGENT APP V2

## MASTER PRODUCTION UPGRADE PROMPT

You are responsible for upgrading the **existing DairyOne application** into a production-grade, intelligent, real-time **Dairy Collection Agent App**.

This is **NOT a greenfield project**.

The existing DairyOne application already contains functionality, workflows, UI, authentication, database structures, routes, trips, farmer management, collection flows, maps, QR scanning, and potentially offline functionality.

Your job is to **audit, preserve, improve, extend, and integrate** the current system.

---

# 0. NON-NEGOTIABLE RULE — DO NOT REBUILD FROM SCRATCH

Before writing or replacing code:

1. Inspect the entire existing DairyOne codebase relevant to the agent side.
2. Understand the current architecture.
3. Identify existing screens, routes, components, hooks, services, APIs, database tables, relationships, authentication, roles, trip logic, route logic, farmer logic, collection logic, QR logic, GPS logic, and offline logic.
4. Identify what is already working.
5. Reuse existing functionality wherever practical.
6. Do not replace working functionality merely for architectural preference.
7. Do not create duplicate database entities when existing ones can be extended.
8. Do not break manager/admin functionality.
9. Keep existing historical data compatible.
10. Use safe, incremental database migrations.
11. Preserve existing URLs/routes/navigation wherever practical.
12. Maintain backward compatibility where required.
13. Do not silently delete existing functionality.
14. Do not rebuild the app from zero simply because a cleaner architecture is possible.

First classify existing functionality as:

```text
KEEP
IMPROVE
EXTEND
REPLACE ONLY IF NECESSARY
```

The final result must feel like **DairyOne upgraded to V2**, not an unrelated replacement application.

---

# 1. CORE PRODUCT VISION

DairyOne Agent App should become:

> **One intelligent app that tells the agent exactly what to do, tells them whether they are on time, tells them how delayed or early they are, verifies where they are, verifies the correct farmer and collection shift, prevents duplicate collection, records everything automatically, tracks the route in real time, explains operational delays, and continues working reliably when the internet is weak or unavailable.**

The agent should never need to wonder:

> What should I do now?

> Where should I go next?

> What time should I arrive?

> Am I on time?

> How many minutes late am I?

> Why am I late?

> Can I recover the delay?

> Did I already collect this farmer?

> Is this the correct shift?

> What should I do if internet is unavailable?

DairyOne should answer these automatically.

# 2.4 DELAY BREAKDOWN

Never simply say:

> Agent is late.

Determine why.

### TRAVEL DELAY

Potential causes:

* Late trip start
* Traffic
* Road blockage
* Wrong route
* Vehicle issue
* Unplanned stop
* Route deviation

### COLLECTION DELAY

Potential causes:

* More farmers than expected
* Farmer issue
* Testing issue
* Equipment issue
* Quantity issue
* Workflow issue

### WAITING DELAY

Track:

```text
Arrival
↓
Collection Start
```

Example:

```text
Arrived: 07:30
Started: 07:42

Waiting: 12 minutes
```

### ROUTE DELAY

Detect:

* Route deviation
* Detours
* Unplanned stationary time

### PREVIOUS STOP DELAY

The system must recognize inherited delay.

Example:

```text
Stop A
+10 min

Stop B
+8 min

Stop C
+6 min
```

The system should understand that Stop B may have inherited the delay from Stop A.

# 2.5 DELAY PROPAGATION & RECOVERY

Original route:

```text
07:00 Stop A
07:30 Stop B
08:00 Stop C
08:30 Stop D
```

After a 15-minute delay:

```text

08:15 Stop C
08:45 Stop D
```

After recovering time:

```text
07:15 Stop A
07:40 Stop B
08:05 Stop C
08:32 Stop D
```

DairyOne should continuously determine:

> Can the agent recover the delay?

Track:

* Delay created
* Delay carried
* Delay increased
* Delay reduced
* Delay recovered
* Remaining route impact

# PHASE 10 — SINGLE COLLECTION PER FARMER PER SHIFT

This is a **mandatory business rule**.

Core rule:

> **A farmer may be collected again in another legitimate shift, but the same farmer must not be accidentally collected twice within the same configured shift and collection cycle/day.**

Example:

```text
MORNING SHIFT

Ramesh Patel
✓ Collected 12.5 L
07:42 AM
```

Trying again:

```text
⚠ ALREADY COLLECTED

Ramesh Patel has already been
recorded for the Morning Shift.

Collected:
12.5 L

Time:
07:42 AM

[ VIEW COLLECTION ]
```

Do not allow accidental duplicate submission.

# PHASE 21 — SHIFT-AWARE COMPLETION LOGIC

A stop is not necessarily complete simply because the agent arrived.

```text

✓ Sita
✓ Mahesh
○ Pooja
```

```text

```

After every farmer is either:

* Successfully collected, or
* Processed through an approved exception workflow

then:

```text
✓ STOP COMPLETE
```

An exception must not silently count as a successful milk collection.

# PHASE 22 — SHIFT BOUNDARY PROTECTION

Handle boundary conditions correctly.

Example:

```text
11:59 AM
→ Morning Shift

12:00 PM
→ No active shift
```

Where a grace period exists:

```text
Morning:
05:00 AM – 12:00 PM

Grace:
12:00 PM – 12:15 PM
```

DairyOne must distinguish:

* Active
* Grace
* Ended
* Upcoming
* No shift

Do not allow shift manipulation to bypass duplicate protection.
