## 2. DESIGN MANDATE

Every agent screen must answer at least one of these questions **at a glance, without reading paragraphs**:

| Question | Design implication |
|---|---|
| What should I do now? | One unmistakable primary action per screen |
| Where should I go? | Distance/ETA always visible near the action |
| Am I early, on time, at risk, or delayed? | A single, consistent status system (see §4) |
| Why am I delayed? | Delay is explained, never just stated |
| Can I safely collect this farmer? | Verification state is visually distinct from "in progress" |
| Will my work be saved offline? | Sync/connectivity state is always visible, never hidden in a menu |

Visual philosophy: **operationally dense, visually calm.** Agents glance at this app while walking, driving, or standing in a farmer's yard — not sitting at a desk. Prioritize scannability over decoration.

## 3. ICON SYSTEM — HARD REQUIREMENT

**Do not use emoji anywhere in the interface** (no 🟢🟡🔴📍🌅🔋🌐✓ etc., including in code, mock copy, empty states, or notifications). The original spec document used emoji as placeholders for status meaning only — replace every single one with a proper icon component.

Build a **custom icon system**:

1. **Icon library base:** Use `lucide-react` (already MIT-licensed, tree-shakeable, consistent 24px stroke grid) as the underlying primitive set, wrapped in DairyOne's own `<Icon />` component so the stroke width, size scale, and color tokens are centrally controlled — this is what makes it "custom" rather than a raw third-party import scattered through the app.
2. **Status icons (replace all emoji status dots):**
   - Ahead / On-time → filled circle-check icon, success color
   - At risk → triangle-alert (outline) icon, warning color
   - Delayed → circle-alert (filled) icon, danger color
   - Offline/pending sync → cloud-off icon, neutral color
   - Verified location → map-pin-check icon
   - Not verified / out of geofence → map-pin-off icon, warning color
3. **Domain icons (replace all object emoji):** shift (sunrise/sunset icon variants for Morning/Evening), battery, signal/Wi-Fi, QR/scan, farmer (user icon), route/map, trip (truck or navigation icon), punch clock, milk (custom SVG if no adequate lucide match — build one flat, single-stroke SVG in the same visual weight as the rest of the set), sync/refresh.
4. **Consistency rules:**
   - One stroke width across the entire icon set (no mixing filled emoji-style glyphs with outline icons).
   - Icons always pair with a text label or are used inside a component that has one nearby — never icon-only meaning for anything status-critical (accessibility).
   - Status is communicated by **color + icon shape together**, never color alone (colorblind-safe).
5. Where no existing icon fits (e.g. a milk can, a collection point marker), design one minimal custom SVG rather than approximating with an emoji or an unrelated stock icon.

## 4. STATUS & COLOR SYSTEM

Define these as design tokens (Tailwind config / CSS variables), reused everywhere — home, trip, stop timeline, collection, sync:

| State | Token name | Suggested color | Used for |
|---|---|---|---|
| Ahead / Success | `status-success` | Green | Ahead of schedule, verified, synced, completed |
| On schedule / Info | `status-neutral-positive` | Teal/Blue-green | Exactly on time |
| At risk | `status-warning` | Amber | Small delay, waiting sync, grace period |
| Delayed / Danger | `status-danger` | Red | Significant delay, blocked action, exception |
| Offline / Inactive | `status-muted` | Gray | Offline mode, pending, disabled |
| Current focus | `status-active` | Blue/Brand primary | Current stop, active shift, in-progress |

Build one reusable `<StatusBadge status="success|warning|danger|muted|active" label="..." icon={...} />` component and use it everywhere instead of hand-rolled colored text/emoji per screen.

## 5. SCREENS TO AUDIT AND REDESIGN

Reference `PHASE 5–9, 39` of the attached master spec (`__DAIRYONE_AGENT_VIEW.txt`) for full behavioral detail; this section defines the **visual/interaction** requirement for each.

### 5.1 Device Readiness / Pre-shift Check
- Checklist card: precise location, background tracking, internet, battery, notifications — each row is an icon + label + status badge, not emoji text.
- Failing items expand inline with a plain-language explanation and a "Fix now" action — never just a red icon with no guidance.

### 5.2 Punch In / Punch Out
- Single-glance card: current time, verified location pin, connectivity/battery icons, scheduled vs actual time, and a status badge (on-time/late) before the confirm action.
- Confirmation state transitions clearly into "ON DUTY" using the active-status token, not a color change alone.

### 5.3 Agent Home ("Command Center")
- Header: greeting, on-duty badge, shift badge (icon-based sunrise/sunset, not emoji), start time.
- **Time Performance card** — the most important card on the screen. Large status badge + delta in minutes + (if delayed) where the delay started and recovery potential, in a secondary line, not buried.
- **Next Action card** — the primary action. Destination, farmer count, distance, ETA, and status badge, with one dominant CTA button.
- **Today's Performance strip** — compact stat row (liters, farmers, value, stops, delay) using consistent numeral typography, not mixed with icons.
- **System Status bar** — persistent, low-profile strip (not a modal) showing GPS tracking, sync state, battery — always visible, collapses to a thin bar on scroll rather than disappearing.

### 5.4 Trip & Route
- Progress indicator: replace dot-emoji progress (`● ● ● ○ ○ ○`) with a proper segmented progress bar component with a numeric "X / Y stops" label.
- Live Trip Status card: on-track/behind badge, scheduled vs expected completion, delta.

### 5.5 Live Map
- Stop pin states (completed / current / pending / problem) as distinct icon+color pin markers, not colored emoji circles — define a `<StopPin state="..." />` marker component reused on map and in the timeline list.

### 5.6 Stop Timeline
- Each stop is a row/card: name, status badge, scheduled vs arrived/ETA, delta — consistent layout for completed, current, and upcoming states so the eye can scan down the list quickly.

### 5.7 Arrival Detection / Location Verification
- Clear binary state design: verified (icon + distance) vs not verified (icon + distance + two actions: navigate / report exception). Avoid ambiguous middle states without an explicit label.

### 5.8 Farmer Verification & QR
- Scan screen: full-bleed camera view with a minimal frame overlay (no decorative emoji instructions).
- Post-scan result card: farmer name/code, current shift badge, collection status, single CTA.
- Duplicate-collection state must look **structurally different** (locked icon, muted background) from "pending" and "verified" — an agent should never be able to mistake it for a normal state at a glance.

### 5.9 Collection Save Confirmation
- Success state: quantity, timestamp, confirmation icon, single "Next Farmer" CTA. Keep this screen the fastest to parse in the whole app — it repeats dozens of times per shift.

### 5.10 Stop Completion Summary
- Stat block (farmers collected / expected, stop delay, route delay, potential recovery) using the same status-badge and typography system as the Home screen, so numbers are trustworthy and consistent across screens.

### 5.11 Offline / Sync State
- Persistent, non-intrusive indicator (status bar or toast, not a blocking modal) showing "N items waiting to sync" with reassuring copy ("Your work is safely saved") and an icon-based offline indicator, never a bare emoji.

### 5.12 History & Profile
- Apply the same card/list patterns and status tokens established above rather than inventing new ones — this is where inconsistency usually creeps in.

## 6. INTERACTION & MOTION GUIDELINES

- One primary CTA per screen, fixed near the thumb zone (bottom of screen on mobile).
- Status changes (on-time → at-risk → delayed) should transition with a brief color/icon crossfade, not an abrupt jump — this is a field app, sudden red alarms should feel informative, not alarming.
- Loading and syncing states use skeleton placeholders matching final layout, not spinners alone.
- Respect existing navigation structure (§1) — do not introduce a new nav pattern unless the audit shows the current one is broken.
